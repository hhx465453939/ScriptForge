# 指标族与「爆」的量化判据

> 本文件是运营作战台的**目标层**。没有这一层，后面所有阶段都是无靶射击。
>
> 一句话：**爆不是形容词，是一个可计算的判定式。**

---

## 0. 为什么必须先定指标

改造前的项目里有「六维/七维评分」，那是**我们自造的代理指标**——精细、可复现，但从未被证明与真实结果相关。

本文件解决的是它上游那一步：**先规定"要什么"，再规定"怎么量"。**

两者的分工：

| 层 | 问的问题 | 归属 |
|---|---|---|
| 目标层（本文件） | 这个战役要**赢什么指标** | 由人定，写进 `00-brief.md` |
| 代理层（`math-engine.md`） | 这条内容在结构上**强不强** | 由引擎算 |

代理分高 ≠ 目标达成。必须靠 S7 回填去验证两者的关系。**这一条不许混。**

---

## 1. 四种目标对象（冻结）

```yaml
obj_type: repo | content | product | personal
```

| obj_type | 典型场景 | primary_metric（唯一胜负指标） | secondary_metrics（只做诊断） |
|---|---|---|---|
| `repo` | 把开源项目运营火 | `stars` | forks / issues / prs / 日增 star / 榜单出现 / watchers |
| `content` | 做账号、涨流量 | `views` | 完播率 / 互动率 / 收藏率 / 涨粉数 / 主页点击 |
| `product` | 卖货 | `sales` | 点击率 / 加购率 / 转化率 / 客单价 / ROI |
| `personal` | 个人品牌 | `followers` | 主页点击 / 搜索指数 / 提及量 / 私信咨询 |

**硬规则**：`primary_metric` **只能有一个**。想同时赢两个 = 没有优先级 = 无法归因。

如果确实要双目标，拆成两个 campaign，而不是塞进一个。

---

## 2. 「爆」的量化定义（唯一判据）

```
爆 := primary_metric 在「同 obj_type + 同形态 + 同渠道」的历史序列中 ≥ P80
      且必须回带 n（样本量）与置信区间
```

三个条件缺一不可：

1. **同条件**：不能拿抖音播放量比公众号阅读量；不能拿 0 粉账号比 10 万粉账号
2. **P80 而非绝对值**：因为不同账号基线完全不同，绝对值无意义
3. **带 n 与区间**：n 小的 P80 不可信，区间宽就是在告诉你"别当真"

### 2.1 分位计算（与引擎对接）

- 用 `viralmath.uncertainty.quantile` 算 P80（线性插值）
- 用 `viralmath.uncertainty.bootstrap_ci` 给 P80 的 95% 区间
- 样本量 `n < 10` → 判据**降级为「观测模式」**：只记录，不下「爆/不爆」结论
- 无历史序列 → `baseline: BASELINE_MISSING`

### 2.2 降级阶梯（不许跳过）

| 情形 | baseline 值 | 允许的结论 |
|---|---|---|
| n ≥ 30 | `{p50, p80, n}` + CI | 可判定「爆 / 未爆」 |
| 10 ≤ n < 30 | `{p50, p80, n}` + 加宽 CI | 可判定，但必须标注「样本偏少」 |
| n < 10 | `{p50, p80, n}`，标 `LOW_N` | 只可给「相对位置」，不可下定性结论 |
| 无历史 | `BASELINE_MISSING` | **本次 campaign 只能产出假设，不得宣称成功** |

## 3. 指标采集口径（防口径漂移）

口径不统一，回填就是垃圾进垃圾出。

### 3.1 content

| 指标 | 口径（必须写清） |
|---|---|
| `views` 播放/阅读 | 平台后台「播放量」（抖音）或「阅读量」（公众号/知乎）；不看第三方估算 |
| 完播率 | 「完整播放次数 / 播放次数」；短于 100% 的进度按平台默认 |
| 互动率 | `(点赞 + 评论 + 收藏 + 转发) / views`；分子分母必须同窗口 |
| 收藏率 | `收藏 / views`（小红书核心指标，权重高于点赞） |
| 涨粉数 | 该条内容带来的**净增关注**（若平台不给，写 `UNKNOWN`） |

### 3.2 repo

| 指标 | 口径 |
|---|---|
| `stars` | 仓库累计 star 总数 |
| 日增 star | 当日新增 − 当日取消；用当日快照相减 |
| 榜单出现 | 记录出现在哪些榜、哪一天、什么位置（趋势榜/日榜/周榜） |
| issues / prs | 累计数；区分外部贡献者与自建 |

**观测窗口**：`repo` 建议以「发布/推广动作后 7 天」为窗口，因为 star 增长有尾部长尾。

### 3.3 product

| 指标 | 口径 |
|---|---|
| `sales` | 成交件数（不是 GMV；GMV 受价格波动干扰） |
| 点击率 | 商品卡点击 / 曝光 |
| 转化率 | 成交 / 商品卡点击 |
| ROI | 增量 GMV / 投放花费（必须说清是否含自然流量） |

### 3.4 personal

| 指标 | 口径 |
|---|---|
| `followers` | 净增关注（涨粉 − 掉粉） |
| 主页点击 | 从内容进入主页的次数 |
| 搜索指数 | 平台或第三方提供的搜索热度；注明数据源层级 |

## 4. 回填字段字典（与 `assets/publish-ledger.md` 对齐）

每行回填记录必须含下列字段，缺一即该行作废：

| 字段 | 类型 | 说明 |
|---|---|---|
| `row_id` | string | 唯一行号，与物料文件 id 对应 |
| `campaign` | string | campaign slug |
| `asset_file` | string | 对应 `04-scripts/` 或 `05-assets/` 的文件名 |
| `platform` | string | 发布渠道（douyin / xiaohongshu / …） |
| `published_at` | date | 实际发布日（不是计划日） |
| `primary_value` | number | 主指标数值 |
| `secondary_values` | object | 辅助指标键值对 |
| `window` | object | `{start, end}` 观测窗口 |
| `source_level` | `L1` \| `L2` \| `L3` | 数据来源层级（见 §5） |
| `baseline_at_publish` | object | 发布时的基线快照（防事后篡改比较基准） |
| `hypothesis_id` | string | 本条要验证的假设编号（见假设台账） |
| `notes` | string | 异常说明（限流/违规/撞热点等） |

**为什么要 `baseline_at_publish`**：如果基线事后被更新，再拿旧数据比新基线，会得出假的「爆了」。快照能防这个。

---

## 5. 数据来源分级（强制）

| 层级 | 来源 | 可信度 | 使用限制 |
|---|---|---|---|
| `L1` | 平台官方后台截图/导出、GitHub API、官方开放平台 | 高 | 可直接用于判定 |
| `L2` | 第三方工具估算、搜索到的公开报道 | 中 | 只能做参考，**不得单独用于「爆/不爆」判定** |
| `L3` | 用户口述、人工观察 | 低 | 只能做方向性输入，必须标注 |

**硬规则**：每条数据必须带 `source_level`。无层级的数字**不许进表**——这是本文件最重要的一条。

---

## 6. 常见错误（每一条都真实发生过）

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 把辅助指标当胜负 | 「播放很高但零转化」被判定为成功 | 胜负只看 `primary_metric` |
| 用绝对值比不同账号 | 小号永远"没爆" | 只比自身历史分位 |
| 事后修改基线 | 得出假的「爆」 | 必须在发布时快照 `baseline_at_publish` |
| 混淆代理分与目标分 | 七维 80 分却被当成"会爆" | 代理分只描述结构强度 |
| 窗口不一致 | 拿 30 天数据比 7 天基线 | 窗口写进字段，比对前先校验 |
| 编造缺失值 | 整条信任链崩塌 | 写 `UNKNOWN` 并降级结论 |

---

## 7. 从 0 到有基线（第一次跑怎么办）

第一次做 campaign 时没有历史序列，按这个顺序走：

1. **S0 写 `baseline: BASELINE_MISSING`** —— 诚实记录
2. **本 campaign 定位为「基线采集战役」**：目标是**产出 n≥10 的样本**，而不是"爆"
3. **发布 10–15 条**（不同形态/渠道组合），全部回填
4. **第一次校准**：算出 P50/P80，写入 `baseline`
5. **下一个 campaign 才具备判定能力**

**这一步不能省**。跳过它直接宣称"爆了"，就是回到拍脑袋。
